# 竹山同城 · 微信小程序开发 PRD v1.1

> 本文以原《竹山同城 PRD》为需求来源进行工程化修订，目标是让开发者或 AI 编程 Agent 能按模块实现、联调和验收。本文保留“便民信息 + 商家优惠 + 社区”的产品方向，明确第一版边界、状态、权限、数据和交付标准。原 PRD 中与本文冲突的内容，以本文为准。

> **产品决策前提：**先读同目录《竹山同城_商业闭环与小程序功能设计.md》。本文件定义可实现的能力，首批地区、分类、商家和首页主入口应根据现有用户渠道与商家资源确定；不能把栏目开发完成当作产品价值或商业闭环已成立。

> **商家合作补充：**店与店之间可直接购买推广/有效引流服务；平台提供合作、来源记录、排名与对账。报价、有效结果和榜单规则见同目录《竹山同城_商家互相拓客与排名机制_v0.3.md》；本文件第 9 节补齐相应能力。

## 0. 项目目标与版本边界

### 产品目标

居民在竹山县微信小程序中浏览和发布当下有效的本地信息；在 A 店扫福利码后先看到并可当场使用 A 店券，再看到经 A 店同意展示的 B/C 合作店券。服务类优惠支持预约到店；商家入驻、建券、确认预约和核销；管理员审核商家与信息并处理举报。首批上线集中在一个地区和少数可维护供给的分类，后续配置扩展到全县。

### 版本划分

| 版本 | 必须完成的业务闭环 | 明确不包含 |
|---|---|---|
| V1.0 上线版 | 便民信息浏览/发布/审核；商家入驻/审核；门店福利码（本店当场券＋合作店券）；领券/预约/核销；商家合作单、来源记录、引流排名与结果对账；基础管理 | 在线支付、付费置顶、自动分润、提现、完整社区、拼团 |
| V1.1 在线交易版 | 套餐/置顶支付；商家合作在线付款与结算接入；效果报表增强 | 线上结算的资金路径须按实际支付产品与商户身份确认 |
| V1.2 社区版 | 邻里帖、评论、点赞、话题、商家动态 | 绿松石交易或鉴定服务须单独立项 |

V1.0 的合作券由双方商家确认后展示，可约定免费互推或付费推广。系统记录合作条件、应付账单与双方确认的实际收付，不自动分账或提现。原文第 13 与第 15 节的阶段冲突，以本版划分为准。

### 地域数据修正

原文“9 镇 5 乡”需修正。竹山县人大公开材料写全县 17 个乡镇。地区选项由后台配置和行政区划数据生成，不能硬编码数量。上线前核对乡镇名称与编码。来源：[竹山县人大常委会公报](https://www.zsrdw.gov.cn/Image_News/202408/2024080211024588507.pdf)。

## 1. 技术决策

| 项目 | V1.0 决策 | 原因/限制 |
|---|---|---|
| 客户端 | uni-app、Vue 3、TypeScript、Pinia，先编译 `mp-weixin` | 原 PRD 的框架可用；官方文档支持该组合。H5 待单独设计身份与调用方式 |
| 后端 | 微信云开发：云函数、云数据库、云存储 | 小程序直接调用云函数，服务端从可信上下文取得用户身份；不由前端传 `openid` 作为身份依据 |
| 管理端 | V1.0 先做受角色保护的最小管理页面；完整 PC 后台在 V1.1 | 先保证审核和投诉能运行，再扩展复杂后台 |
| 接口层 | 客户端定义 TypeScript 服务接口；`mock` 和 `cloud` 两个适配实现 | 页面不感知数据来源；Mock 可用于页面开发，但上线验收必须连接真实云环境 |
| 支付 | V1.0 先做合作账单、核对和实际收付记录 | 线上付款与结算在 V1.1 按支付产品能力接入 |

技术参考：[uni-app Pinia](https://uniapp.dcloud.net.cn/tutorial/vue3-pinia.html)、[uni-app 路由与 tabBar](https://uniapp.dcloud.net.cn/collocation/pages.html)、[微信小程序调用云函数](https://docs.cloudbase.net/en/recipes/add-cloud-function-wechat-miniprogram)。开发前固定依赖版本并记录在锁文件中。

**注意：**原 PRD 同时写 REST `/api/*` 和微信云函数。V1.0 以云函数为实际传输方式，`/api/*` 只作为业务服务方法的概念命名；不要做一套未使用的 HTTP 后端。若后续需要 H5/PC 共用接口，再提供受鉴权保护的 HTTP 网关。

## 4. 关键业务规则

### 4.1 便民信息状态

`DRAFT → PENDING → APPROVED / REJECTED → OFFLINE / EXPIRED`

- 用户提交后进入 `PENDING`。V1.0 租房、二手及新用户前三条均人工审核；其他类也先进入审核队列，待运营验证自动审核可靠后再决定放开。这样统一原文第 7 与第 12 节的冲突。
- 已发布信息编辑标题、正文、图片、价格、联系方式后回到 `PENDING`；审核前仍展示上一已审核版本，或暂时下架，二选一需在实现时固定。V1.0 选择**暂时下架**，规则最简单。
- 举报不能立即证明违规；管理员处理后可下架。删除采用软删除并保留必要审计记录。
- 每条信息有 `expires_at`，到期自动隐藏，用户可以在“我的发布”手动刷新并重新审核。

### 4.2 商家状态

`PENDING → APPROVED / REJECTED → SUSPENDED`。只有 `APPROVED` 能公开展示、建券和核销；`SUSPENDED` 时公开券停止领取，已领取券的处理需管理员按实际情况处置并通知相关用户。

### 4.3 优惠券状态与库存

- 券模板：`DRAFT / ACTIVE / PAUSED / ENDED`；用户券：`UNUSED / USED / EXPIRED / VOID`。过期判定以服务端当前时间为准；定时任务只负责物化状态，不是唯一校验。
- `claimed_count` 表示已发放数量，`redeemed_count` 表示已核销数量；两者不可混用。库存扣减、单人限领检查、生成用户券在同一事务或等效原子流程完成。
- 核销为幂等操作：同一用户券只能从 `UNUSED` 成功转为 `USED` 一次，同时写入一条核销记录。并发双击或重复网络请求不得产生双核销。
- 用户券快照保存领取时的券标题、优惠规则和有效期，防止商家修改模板后改变既有用户权益。
- 每张券明确 `usage_mode = INSTANT / WALK_IN / BOOKING`。`INSTANT` 允许顾客在发券商家当场领取并核销；`WALK_IN` 供以后到店使用；`BOOKING` 要求先完成预约确认。服务端校验核销店铺与券所属商家一致。
- A 店当场券的成本由 A 店承担；其券规则需明确是满额/加购、复访回馈还是其他目的。看板不把“本来已进店的顾客拿到折扣”算成 A 店新增客流。
- 核销错误：券不存在、非本店、已用、过期、未生效、商家无权、券被停用，均返回独立业务码和可读提示。

### 4.4 服务类优惠预约与到店

- 仅 `booking_required=true` 的券显示预约入口。V1.0 采用“用户提交期望时段 → 商家确认/拒绝”流程，不开发复杂排班系统；商家必须设置每日接待上限。
- 预约状态：`REQUESTED → CONFIRMED / REJECTED / CANCELLED`；`CONFIRMED → ARRIVED / NO_SHOW / CANCELLED`；`ARRIVED → COMPLETED`。具体变更权限由服务端控制；到店与核销分别记录，不把预约成功当成实际到店。
- 商家确认预约后，用户可见店铺、时段和券规则；商家拒绝时给出原因并允许重新选择。超时未处理的预约由运营后台提醒。
- 商家在用户到店后确认是否为首次到店；该标记属于商家声明，数据报表应注明“商家确认”，不能当作独立验证的成交额。首访消费、后续复访只在商家愿意提供可核对数据时记录。
- 平台与合作店之间不直接交换原店客户名单。预约联系信息只给承担接待的商家和必要的运营人员，并遵守告知与授权要求。

### 4.5 二维码与扫码来源

- 商家码的 `scene` 使用短 token；服务端映射到来源商家和福利页配置，避免依赖前端拼接长参数或暴露可篡改的商家 ID。
- 从 A 店码进入时落到 **A 店福利页**，先展示本店可当场使用的券，再展示经配置的 B/C 合作店券。展示与领取均保留来源店 A；B/C 店券在 B/C 店核销。用户从其他入口重新进入后，来源归因按明确的有效扫码窗口和服务端记录执行。
- 重复 `onLaunch/onShow` 不应重复计一次扫码。日志记录码、来源、时间和必要的去重标识。扫码、A 店当场核销、B/C 店领券、B/C 店到店与核销分别统计。
- 扫码本身只用于统计。付费合作账单按双方接受的合作单与有效结果规则生成；同一合格新客不重复收费，异常/退款按约定剔除，具体要求见第 9 节与 v0.3 合作说明。

## 5. 数据模型与索引

字段沿用原 PRD 第 9 节，并做以下必需修订。每个集合含 `created_at`、`updated_at`、软删除/状态字段；时间统一以服务端存 UTC，界面按中国标准时间显示。

| 集合 | 核心字段/新增字段 | 关键索引或约束 |
|---|---|---|
| `user` | `openid`、状态；手机号可选 | `openid` 唯一 |
| `merchant` | 所有者、审核状态、品类、地区、营业信息 | 所有者与状态索引 |
| `merchant_staff` | `merchant_id`、`user_id`、角色、状态 | `(merchant_id,user_id)` 唯一 |
| `info` | 发布者、类别、地区、审核状态、`expires_at`、`contact_consent` | `(status,category_id,town,created_at)`；发布者索引 |
| `coupon` | 商家、规则、`usage_mode`、`claimed_count`、`redeemed_count`、总量、限领、起止时间、状态 | `(merchant_id,status,end_time)` |
| `user_coupon` | 用户、商家、券、来源商家、合作单、唯一券码、规则快照、状态、领取/使用时间 | `code` 唯一；`(user_id,coupon_id)` 查询索引 |
| `benefit_placement` | 来源商家、目标券、位置排序、展示起止时间、双方确认状态 | `(source_merchant_id,status,sort)`；禁止配置已停用券 |
| `appointment` | 用户券、商家、期望时段、确认时段、状态、拒绝原因、首次到店声明、到店时间 | `(merchant_id,status,requested_at)`；每张用户券最多一个有效预约 |
| `scan_token` | token、类型、目标 ID、状态 | token 唯一 |
| `scan_log` | token、来源商家、去重标识、时间 | `(token,created_at)` |
| `verify_log` | 用户券、商家、核销员工、时间 | `user_coupon_id` 唯一 |
| `report` | 举报人、对象、原因、状态、处理记录 | `(status,created_at)` |
| `audit_log` | 操作者、动作、对象、前后摘要、时间 | `(target_type,target_id,created_at)` |

具体索引能力、事务范围和数据库规则随最终云数据库环境确认。任何索引都不能代替云函数中的权限检查。

## 6. 服务接口契约

页面只调用 `src/services` 的类型化方法。云函数按 `module + action` 或独立函数组织，统一返回 `{ code, message, data, requestId }`。列表返回 `{ list, page, pageSize, total, hasMore }`。所有服务端错误记录 `requestId`，界面不展示内部异常栈。

| 模块 | V1.0 方法 | 约束 |
|---|---|---|
| `auth` | `getSession`、`getProfile` | 服务端获取可信身份；手机号授权单独处理，浏览不依赖手机号 |
| `info` | `list`、`detail`、`create`、`update`、`mine`、`offline`、`report` | 公开查询只返回已审核内容；写操作校验所有者 |
| `merchant` | `list`、`detail`、`benefitPage`、`apply`、`mine`、`update`、`getCode` | 福利页只返回本店有效券与经确认展示的合作券；审核状态和所属关系由服务端校验 |
| `coupon` | `listByMerchant`、`create`、`pause`、`receive`、`mine`、`verify`、`verifyLogs` | 不信任前端传入的身份、库存和核销状态 |
| `appointment` | `request`、`mine`、`merchantList`、`confirm`、`reject`、`cancel`、`markArrival`、`markNoShow` | 服务类优惠使用；商家仅操作本店预约，居民仅查看/取消自己的预约 |
| `admin` | `reviewMerchant`、`reviewInfo`、`handleReport`、`suspendMerchant`、`setCategory`、`setBenefitPlacement` | 合作券展示需双方商家确认；每次操作校验管理员角色并写审计日志 |
| `tracking` | `enterByCode` | 服务端解析 token，限流并去重 |

原 PRD 中 `POST /coupon/receive` 同时出现 `coupon_id`/`couponId` 和客户端 `openid`，本版统一服务方法入参为 `{ couponId }`；身份由服务端取得。归因来源来自服务端解析的有效扫码记录，而非客户端任意传 `sourceShopId`。

### M0：可运行骨架

创建工程、锁定依赖、配置 `pages.json`、环境变量模板、云环境初始化、统一错误组件、Mock/Cloud 服务切换。验收：微信开发者工具能打开首页；基础路由、空状态、加载状态正常；无真实密钥入库。`tabBar` 页面跳转使用 `switchTab`。

### M1：身份、商家与福利码

完成匿名浏览、必要身份建立、商家入驻/审核、店铺详情、门店福利码生成和落地、扫码统计。验收：未审核商家不可被搜索；A 店码准确打开 A 店福利页；失效码有可恢复的提示页。

### M2：本店当场券与跨店优惠闭环

完成 A 店当场券、合作店 B/C 券的展示配置、领券、券包、到店核销、来源统计。验收：从 A 店扫码能当场领取并核销 A 店券，也能领取 B/C 店券并仅在各自店铺核销；无效券不展示；库存并发、限领、双击核销和网络重试按状态机处理。

同一里程碑补齐商家合作的发布/接受、结果核对和引流榜。没有真实数据时显示空状态或“新加入”，不生成虚构名次与成绩；付费合作的应付与实付分开。

### M3：服务预约与便民信息

完成服务类优惠预约/商家确认、商家基础看板，以及地区筛选、便民信息列表/详情/发布/审核/我的发布/举报。验收：预约成功、实际到店与核销分开统计；未审核信息不公开；非所有者不能编辑；被拒绝可见原因；过期信息不出现在公共列表。

### M4：联调与上线准备

接真实云环境，补齐管理审计、隐私告知、投诉处理、异常日志、备份与恢复说明；在真机上跑通居民和商家两条完整路径。验收：不依赖 Mock；核心流程有测试数据和人工验收记录；运营主体完成必要资质核查后再提交审核发布。

每个里程碑交付：代码、环境配置样例、数据结构变更、运行方式、测试结果和未解决问题。页面截图只能证明展示，不能代替云函数和真机流程验收。

## 8. 上线门禁与待确认项

### 上线门禁

1. **安全：**写接口逐项验证身份与所属；后台仅管理员可见；券码不能越权核销；日志不泄露手机号、openid 或其他敏感值。
2. **数据：**审核前内容不公开；券库存和状态一致；列表分页不重复/漏项；二维码映射可撤销。
3. **隐私：**手机号、位置、扫码记录和公开联系电话明确用途、告知、保留和删除方式，按最小必要原则实现。参考：[《个人信息保护法》](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)。
4. **运营：**有人能审核商家与信息、处理举报和停用违规券；审核积压和异常有提醒。
5. **真实环境：**在微信开发者工具及至少一台真机完成扫码、图片上传、登录、领券、服务券预约/确认/到店和核销验收。

### 启动开发时使用的默认假设

| 待确认 | 默认处理 |
|---|---|
| 小程序主体与 AppID | 先用开发环境占位配置，无法真实发布前须填写并验证 |
| 云开发环境 ID | 用环境变量和样例文件；不写死在源码 |
| 品牌名称、Logo、视觉规范 | 暂用“竹山同城”和中性视觉；可替换的主题变量 |
| 乡镇与分类数据 | 后台配置；招聘默认关闭发布 |
| 管理员与商家审核人员 | 初始化角色配置，不在前端写死白名单 |
| 微信支付与收费 | V1.0 记录商家合作条件、账单与双方确认的实付；线上付款单独接入 |

以上假设不阻止 M0～M3 开发，但真实发布前必须逐项确认。本文不把原 PRD 中“非预付卡”“平台不碰资金”“两级以内返佣”等表述视为已完成的法律判断；实际收费与线上结算启用前分别核实合同、收付和具体业务责任。

## 9. 商家之间的拓客合作与排名

### 商家自主合作

每家店都可发布“我要拓客”，也可通过“我要帮店推广”承接其他商家的合作。合作单固定买方店、来源店、券、周期、计费方式、预算、有效结果条件、平台费用和争议处理；双方确认后版本冻结。合作券上架由双方确认，平台审核，替代完全依赖管理员人工配对的方式。

首版支持按位置/周期和按有效新客结果两种合作类型；每单明确一种主要计费依据。按结果合作的预算名额和已发券承诺必须一致，不在顾客到店后才追溯改变条件。

### 三类排序

1. **商家引流贡献榜：**最近 30 天有效新客结果、品类/地区筛选、样本量、退款/争议扣除、暂无足够样本提示。扫码、领券、核销不相加作贡献分。
2. **商家合作机会排序：**可按合作报价、历史有效结果、距离/品类筛选；展示剩余预算、有效条件和付款约定，帮助来源店选择合作。
3. **居民看到的店铺与优惠：**按地点、可用时间、热门等清楚口径展示；付费/竞价推荐标明“广告”，其排序不能当作口碑分或服务认证。参考[《互联网广告管理办法》第九条](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fgs/art/2023/art_d93a579afd45413e8576e4623fab348f.html)。

### 数据与验收补充

新增 `cooperation_offer`（拓客需求）、`cooperation`（双方确认的条件版本）、`cooperation_result`（有效结果及核对状态）、`cooperation_bill`（应付/实付、平台费用、争议记录）。榜单可直接聚合已核对结果；数据量增加后再加入排名快照。

服务接口补充：`cooperation.publish/list/accept/pause/results/confirm/dispute/bills` 与 `ranking.referral/opportunities/consumer`。授权分别校验买方、来源店和管理员；店铺不得修改其他店的报价、归属或结果。

关键验收：领取目标券绑定有效合作来源后不被重复扫码覆盖；同一人、同一目标店的同一新客期不重复结算；自刷、取消、退款等异常按冻结规则处理；榜单只统计对应口径的有效结果；实付状态须有核对依据，不由前端随意标记。
