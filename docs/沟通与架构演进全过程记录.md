# 竹山同城 · 沟通与产品架构演进全过程纪要

> 整理日期：2026 年 11 月 20 日  
> 项目代号：`zhushan-city`  
> 参与者：项目发起人（用户）、Codex、Antigravity (AI 架构师与开发 Agent)

---

## 一、 项目背景与起点

项目旨在面向湖北省十堰市竹山县（辖 17 个乡镇）打造一个集“本地便民信息聚合 + 商家联盟拓客 + 社区互动”三合一的县域生活服务平台。

最初的原型 PRD 规划了：
1. 便民信息（租房、二手、招聘、家政、绿松石名片等）；
2. 商家联盟（商家发券、居民领券、核销、异业互推、平台分润）；
3. 社区（邻里圈、动态、话题）；
4. “一张码”打通线下场景。

---

## 二、 第一轮沟通：专家视角初审与技术合规预警

在对原始 PRD 进行首轮技术与产品专业审查时，识别出了 4 个关键隐患与暗坑：

1. **微信二维码 `scene` 32 字符超标风险**：
   - 原始文档写的 `scene` 参数形如 `t=public&loc=XX小区`，中文字符经 URL 编码后极易超出 32 字符限制导致生成二维码失败。
   - **对策**：建立 `scan_token` 短 Token 映射体系。
2. **小程序类目与资质合规大坑（随时面临微信拒审）**：
   - 便民信息流涉及 UGC 发帖，微信审核极易要求《增值电信业务经营许可证》（ICP/EDI）或网信办安全评估；
   - 招聘类目强制要求人力资源服务许可证。
   - **对策**：MVP 阶段坚决冻结招聘分类，便民全量人工审核，关停社区发帖，保住小程序过审生命线。
3. **资金分润与“二清”金融合规红线**：
   - 平台若私设资金池代转商家互推提成，属于严重违规二清。
   - **对策**：MVP 阶段不碰在线资金分润，降级为“对账单确认 + 线下结算”。
4. **商家冷启动痛点**：
   - 县城小商家对掏年费买软件意愿极低，必须由运营人员“代入驻、代发券”，拿着做好的实体码去地推。

## 三、 第二轮沟通：与 Codex 碰撞出新的商业闭环

用户随后与 Codex 深入讨论并产出了《竹山同城产品与商业闭环完整方案 v1.0》，彻底跳出了传统县城平台“假大空与自嗨”的误区，确立了以**“A店当场券 + 跨店拓客”**为核心的实战机制：

1. **线下真实启动场景**：
   - A 服装店在收银台或试衣间放置专属福利码；
   - 顾客扫码首先领取并当场使用 A 店试衣立减券（例如满 200 减 20）；
   - 在该落地页同时展示经 A 店同意的少量互补好店（如 B 美业 38 元体验、C 足浴 68 元体验）。
2. **点对点拓客采购单**：
   - B 店向 A 店购买精准新客带客服务，按有效结果（到店核销新客）或按周期展示计费，平台提供中立对账凭证与排名。
3. **彻底收敛 MVP 范围**：
   - 坚决不做在线自动分润、不做泛社交、不画虚假成交额大饼，专注于跑通核心的领券、预约、核销与对账。

## 四、 第三轮沟通：DBS（数据、商业、场景）三维碰撞与 5 大精益优化

结合数据库系统架构（Database）、深度商业战略（Business）与微观场景执行力（Scenario），提出了 5 大落地优化：

1. **商业防赖账补丁（预算托管预存池）**：
   - 杜绝“先享受引流、月底再付款”的赊账模式；B 店买拓客需先锁定托管预算，每核销一个自动扣划，消灭 90% 的月底扯皮。
2. **跨店券“限时激活锁”**：
   - 避免跨店券在券包里沉睡 30 天被遗忘，加入“离店专属·今日/48小时有效”的倒计时强激活机制。
3. **微信订阅消息强约束**：
   - 在服务类券预约流中，强制接入 `wx.requestSubscribeMessage`，确保商家确认接单后能直接在微信聊天列表中推送到顾客。
4. **数据架构补全（`merchant_daily_stat` 日汇总表）**：
   - 避免在云数据库中跑多表实时大聚合导致超时，设计每日定时物化汇总表，毫秒级响应商圈引流榜。
5. **冷启动定向撮合（1+1 黄金结对）**：
   - 上线首周不做全城网状匹配，集中打通【女装店 ↔ 美甲店】或【洗车店 ↔ 茶舍】，打磨出标杆后再全城推广。

## 五、 第四轮沟通：工程化全面落地（Zhushan-City MVP）

依据上述所有共识，完成了工程代码开发：
- **前端技术栈**：uni-app + Vue3 + TypeScript + Pinia
- **后端架构**：微信云开发（云函数 + 云数据库）+ 本地高质量 Mock 适配层
- **核心文件**：共 48 个工程文件，涵盖 12 个页面路由、7 个 TypeScript 类型模块、3 个核心组件、5 个生产级云函数。
