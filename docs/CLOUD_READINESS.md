## 已准备的代码

`pnpm run build:mp-weixin` 会在 `dist/build/mp-weixin` 内放入 `cloudfunctions/`，并在生成的 `project.config.json` 中写入 `cloudfunctionRoot`。每个函数有锁定的 `wx-server-sdk` 依赖和 lockfile。当前代码包括：

| 函数 | 已实现的主要约束 |
|---|---|
| `login` | 从微信上下文取身份；用户 ID 确定生成，不能由客户端自设管理员角色 |
| `scanResolve` | 短 token 映射、审核状态校验、五分钟去重、当前来源记录 |
| `merchantCode` | 已审核门店的所有者/员工/管理员可生成带可信短 token 的小程序码；按开发/体验/正式版本缓存图片 |
| `couponClaim` | 忽略客户端自报来源；事务内校验限领、库存、有效期、商家与合作名额；重复请求返回同一张券 |
| `appointmentManage` | 联系方式同意、每日接待上限、预约状态和店员权限 |
| `couponVerify` | 核销店与店员权限、预约到店、事务内单次核销与唯一日志 |
| `getMyCoupons`、`couponVerifyLogs` | 只读本人券包和有权操作的本店记录 |
| `merchantManage`、`couponManage` | 商家入驻与变更审核、公开状态、券模板创建与停用 |
| `staffManage` | 店主生成一次性邀请、独立员工身份接受与权限撤销 |
| `configManage` | 乡镇与分类启停、管理员审计；新发布和入驻按有效配置校验 |
| `userManage` | 管理员按用户编号停用/恢复、处理依据和审计；主要写入口拒绝停用账号 |
| `infoManage` | 信息待审、编辑重审、公开过滤、举报处理和操作审计 |
| `cooperationManage` | 买方发布、入口店接受、平台审核、福利位人工排序/隐藏、结果双方核对、按结果或周期计费、线下实收双向确认 |
| `getShopBenefitData`、`getPromoterRanking` | 仅公开有效券和审核通过门店；榜单只读经确认的统计结果 |
| `statSync` | 中国标准时间日界线，按事件记录生成分项日统计 |

`pnpm run test:cloud` 使用内存数据库验证伪造来源、重复领券、无权限核销、扫码去重、预约容量、商家与信息审核、合作平台审核、结果与账单时点、员工授权、配置启停、停用用户的写入阻断及小程序码权限/缓存。Mock 和 Cloud 两种小程序构建可通过本地编译；这些检查**不能代替微信云数据库事务和真机测试**。

## 上线前必须补齐

云端代码虽然已写入仓库，仍缺**真实权限与事务联调**。员工邀请与撤销、后台地区／分类配置、用户停用、已确认结果的退款与争议更正目前只有本地边界测试；停用商家后已领券处置、真实小程序码生成与扫码、订阅消息模板和完整隐私数据生命周期尚未验收。图片上传已接入 `wx.cloud.uploadFile`，必须在真机确认保存 `cloud://` fileID、展示和删除权限。[图片存储排查](https://docs.cloudbase.net/practices/ai-cli-mini-program)

云函数仍保留 `{ success, ... }` 原始响应以兼容当前页面；客户端适配层会从 `wx.cloud.callFunction` 的 `requestID` 补齐 `code/message/data/requestId`。正式联调时需核对每个业务错误的编号、用户提示和云函数日志关联，再决定是否收敛旧字段。[云函数请求编号与日志查询](https://docs.cloudbase.net/recipes/add-cloud-function-wechat-miniprogram)。合作券由双方接受后再经平台审核上架，管理员可在管理台调整 1–5 的展示顺序或隐藏/恢复。

真实环境须逐项验证：最后一张券的并发领取、每人限领和网络重试；不同店与无权限账号核销；预约容量、拒绝/取消/未到店和重复核销；失效门店码与同人重复扫码；合作来源及预算名额；审核前内容不公开；操作审计；真机扫码、图片上传、通知与已领权益处理。异常日志不应输出手机号、原始 openid 或券码全文。
